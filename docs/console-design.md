## 0. 现在为什么"感觉不对"

不是配色问题，是三件事叠在一起：

1. **层级太深**：底部只有 `Chroot / DSH / 存储` 三个 tab，`体检 / 日志 / 快照 / 设置 / 关于` 全塞进 `⋯` 的一层"更多"，再用栈式路由进去。手机上"想看一眼日志"要两步，且 `⋯` 在右上角，单手够不到。
2. **"DSH" 被当成一个 tab**：但 DSH 不是一类信息，它是一个动作（打开网页）+ 一小块状态（地址、hooks、端口）。占掉一个 tab 的位置，反而把快照/镜像挤没了。
3. **每个动作都像"弹窗审判"**：启动/停止/恢复都先弹一个全屏风险解释，确认后弹一个 "完成（退出码 0）" 对话框要再点一次"好"。但 `start` 要 30–90 秒，这段时间页面是冻结的，用户不知道进度、离开就丢。

一句话：**它是一个"机器的操作面板"，现在做成了"设置 App + 弹窗"。**

## 1. 设计目标

1. **打开三秒内回答三个问题**：在不在跑？能不能用 DSH？出问题按哪个键？
2. **一个页面一个主动作**：主按钮在固定位置，启动/停止互斥，不随状态跳来跳去。
3. **慢操作可见、可离开、可回看**：长任务变成顶部任务条 + 时间线记录，不再是阻塞弹窗。
4. **危险动作解释一次，确认一次**：R3/R4 用半屏说明 + 滑动确认；R0/R1 不打扰。
5. **信息用眼睛扫，不用读句子**：状态点、数字、进度条优先，句子只做补充。

非目标：不做文件管理器，不做终端模拟器，不做 DSH 的第二个前端，不在控制台里实现写分级逻辑（那是 `dsh-ctl risk` 的职责）。

## 2. 用户与场景

只有一个用户：在手机上临时处理 chroot 的本人。三个真实场景决定信息架构：

- **S1 日常**：确认在跑 → 点"打开 DSH"。→ 必须一屏完成，零滚动。
- **S2 坏了**：DSH 打不开 / 状态是 failed / recovery-required。→ 需要"现在发生了什么 + 下一步按哪个"，不能只给原始日志。
- **S3 维护**：更新模块前后，看快照、清磁盘、体检、改自启。→ 低频，允许两步，但要找得到。

## 3. 信息架构：按"层"组织

用户给的心智模型是对的：**这是三层东西，不是四类功能**。控制台按层切 tab，一层一页，每页管自己那层的状态、动作和日志。

| tab | 层 | 这一页回答 | 主要内容 |
|---|---|---|---|
| **设备** | 硬件 | 空间够不够、镜像是哪个、这是什么机器 | 机型/内核/KSU/模块版本、磁盘构成、镜像文件、关键路径 |
| **系统** | chroot | chroot 在不在跑、挂载对不对、快照能不能回 | 状态卡+启停、建议、loop/挂载事实、快照、nsinit/boot/watchdog 日志 |
| **软件** | DSH | DSH 起来没有、地址是什么、hooks/ttyd 什么模式 | 版本、地址与打开、hooks、ttyd、健康检查、重启、DSH 日志 |
| **设置** | 跨层 | 开机怎么办、出问题谁兜底、危险操作怎么确认 | 自启、看门狗、确认策略、对外监听、关于 |

三条规则把"层"真正落到交互上：

1. **tab 顺序自下而上**：设备 → 系统 → 软件。硬件托着系统，系统托着软件；顺序本身就是解释。
2. **每页自带依赖条**：软件页顶部固定一行 `依赖 chroot：运行中` / `依赖 chroot：已停止 → 去启动`；系统页顶部 `镜像：可用` / `镜像：缺失 → 去设备`。下层坏了，上层页面必须直接说"我不能用，因为 X"，而不是显示一个空状态。
3. **日志跟着层走，取消独立日志 tab**：系统页只有 nsinit/boot/watchdog，软件页只有 dsh.log。排查时人已经知道"是系统没起来还是软件没起来"，不需要先选日志类型。全局搜日志的需求用系统页底部的"全部日志"二级页兜底。

导航规则：tab 之间**不保留栈**；二级页（快照详情、全部日志、关于）才用返回栈；tab 根页按返回键退出。

## 4. 分层判据（先定分工，再定页面）

任何新功能先过两道问：

1. **它坏的时候，是整台机器起不来，还是只是某个软件用不了？** 前者归系统层，后者归软件层。
2. **chroot 停止时它还需要可用吗？** 需要 → 必须归系统层（因为系统层的职责就是把机器启动起来）；不需要 → 归软件层。

由此得到两层的职责句：

- **系统层只管四个动词：起停、物资、地盘、体检。** 它不关心 guest 里装了什么软件。
- **软件层只管一件事：这台机器跑起来以后，上面装了什么、什么版本、怎么换。** 它不关心镜像在哪、loop 有没有残留。

## 5. 系统页（chroot 层）

### 5.1 职责

| 动词 | 具体内容 | 现有 `dsh-ctl` 能力 |
|---|---|---|
| **起停** | start / stop / restart / boot / rescue / recover、自启、看门狗 | `start --apply`、`stop`、`restart`、`rescue --apply`、`recover --apply`、`autostart` |
| **物资** | 建镜像、装镜像、换镜像、快照、回滚、清理 | `image create/install`、`snapshot create/list/restore/promote/restore-last-good`、`purge` |
| **地盘** | 镜像/state/workspace/日志的位置与占用、权限修复、备份导出 | `paths --json`、`fixperm`、`log` |
| **体检** | doctor、运行时事实、事后诊断 | `doctor --for-apply`、`status --json`、`plan --check`、`diag` |

系统层**不做**的事（明确写下来，防止以后长歪）：不装插件、不管 DSH 版本、不跑 pnpm、不开终端、不做文件管理。

### 5.2 页面结构

1. **状态卡**：状态点 + `运行中/已停止/启动失败/需要恢复` + `已运行 2 小时 13 分 · holder 28471 · loop7`；主按钮固定位置（启动/停止）；副按钮（打开 DSH / 体检 / 查看建议）。
2. **建议**：doctor 的 FAIL/WARN 转成 `一句话 + 一个按钮`，最多 3 条。
3. **快照**：最近 3 条 + 全部；`last-good` 置顶；行内恢复/设为 last-good/删除。
4. **运行时事实**：镜像、loop、rootfs 挂载、`/data` bind、看门狗——异常项变橙并可点进日志。
5. **诊断入口**：`体检`（doctor 全量）、`生成诊断包`（把这些事实+最近日志打成一个可复制的文本块，贴 issue 用）。
6. **日志尾**：nsinit / boot / watchdog 最近 20 行，全部日志进二级页。

## 6. 软件页（DSH 层）

### 职责

| 组 | 内容 | 现状 |
|---|---|---|
| **终端** | guest shell（s6 起的交互 shell / ttyd）、命令历史、常用命令 | 无控制台入口，需 chroot 侧补 |
| **DSH 本体** | 当前版本、来源、升级/降级、回滚到上一版 | 无控制台入口，需 chroot 侧补 |
| **依赖版本** | `dsh-*` 插件与 pnpm 依赖列表、单包升降、锁版本 | 无控制台入口，需 chroot 侧补 |
| **插件管理** | 已装插件、启用/禁用、安装/卸载、权限预设挂载 | `dsh-run` 已拼 patch，缺列出/查询 |
| **服务** | ttyd 开关、s6 服务状态、端口占用 | `ttyd status/on/off` 已有 |
| **日志** | dsh.log 尾 + 全部 | `log` 已有（需按文件过滤） |

### 页面结构

1. **依赖条**：`chroot 运行中 · 健康` / `已停止 → 去启动`。
2. **DSH 卡**：版本、运行时长、地址（复制/打开）、`hooks: full`、`ttyd: 关`、权限预设；主按钮 `打开 DSH`，次按钮 `重启`。
3. **终端**：`打开终端`（全屏，等宽字体，粘性软键盘工具条：`Tab / Ctrl / ↑ / ↓ / 粘贴`）；可从这里带着命令进（如 `dsh --version`）。
4. **版本**：DSH 版本行 + `升级/降到…`；依赖列表（名称、当前、可升到），单行操作；`回滚到上一版`。
5. **插件**：列表（名称、版本、启用状态），行内 `禁用/卸载`；底部 `安装插件`（输入源或从内置列表）。
6. **服务与日志**：ttyd 开关、s6 服务状态、dsh.log 尾。

所有升降级、插件变更都是 R2/R3：要 reason、要备份点（先自动做一次快照或导出 lockfile）、要可回滚。

## 7. 设备页（硬件层）

1. **排障头**：`PJZ110 · Android 15 (API 35) · 内核 6.6.66 · KernelSU 1.x · 模块 0.2.3`，长按全选复制（贴 issue 用）。
2. **磁盘构成**：横向堆叠条，按 镜像 / 快照 / state / workspace 着色，图例带绝对大小；点击跳到路径。
3. **镜像**：路径、大小、mtime、是否被 loop 占用、`替换镜像`（R3）、`校验`。
4. **关键路径**：`paths --json` 的结果，点按复制。
5. **空间告警**：剩余 < 5GB 时在顶部出一条橙条，带"清理旧快照"入口。

## 8. 交互规范

### 7.1 慢任务（>2s）

- 触发后在**顶部出现任务条**：`启动中… 正在挂载 rootfs（12s）`，右侧 `×` 可隐藏到后台。
- 任务条状态来源于子进程 stdout 的逐行输出，映射成 4–6 个人话步骤；没有匹配行时显示"仍在进行（已 37s）"。
- 完成后任务条变成 3 秒的绿色短条 + 写入时间线；失败变红条，点开看原始输出。
- 同一时刻只允许一个写任务（避免并发 start/stop），其余按钮置灰并提示"上一个操作正在进行"。

### 7.2 风险确认

- R3：半屏 bottom sheet，四段（是什么 / 什么时候用 / 会有什么后果 / 怎么恢复）+ 底部 `滑动确认执行`。
- R4：额外要求输入或长按 3 秒，且控制台不提供"记住选择"。
- R0/R1：不弹 sheet；R1 用一次行内确认（`覆盖？[确认]`）。
- 确认后不再弹"完成"对话框——结果进任务条与时间线。

### 7.3 刷新

- 前台每 3 秒拉一次 `status --json`；退到后台停止；写任务进行中改为 1 秒。
- 支持下拉刷新；任何写操作结束后立即刷新一次。
- 状态未变化时不重组整页（只更新变化的数字），避免 3 秒一次闪动。

### 7.4 文案

- 一律"做什么 + 后果 + 怎么回退"，不写"操作成功"。
- 错误必须带下一步：`启动失败：loop 已被占用。→ 释放 loop（R3） / 查看日志`。
- 数字带单位与人话换算；时间用相对时间（`3 分钟前`），点按显示绝对时间。

## 9. 视觉

- **基调**：深色优先、跟随系统；去掉大面积渐变光斑与玻璃拟态，改纯色背景 + 单层卡片（`#121821` 深 / `#FFFFFF` 浅），仅保留 1px 描边。
- **强调色**：单一系统蓝（深色 `#5C9DFF` / 浅色 `#3482FF`）；状态色只用于状态元素（绿 `#22A06B`、橙 `#FF9F0A`、红 `#E5484D`）。
- **字阶**：28 / 20 / 15 / 13 / 11 sp；行高 1.35–1.45；正文不用全大写、不加字距。
- **圆角与间距**：卡片 22dp，按钮 16dp，页面左右 16dp，卡片内 18dp，块间距 12dp。
- **动效**：状态切换 200ms 交叉淡入；任务条展开 220ms；列表不做逐项入场。
- **图标**：单一线性图标集，24dp，与文字基线对齐；不用 emoji 当图标。

## 10. 无障碍与单手

- 底部 tab 高度 ≥ 56dp，点击区 ≥ 48dp。
- 所有状态不只靠颜色：状态点旁始终有文字。
- 主按钮位于屏幕下半部（拇指区），危险按钮不与主按钮相邻。
- 支持系统字体放大到 1.3× 不截断（避免固定高度卡片）。
- 每个可点卡片都设置 `contentDescription`。

## 11. 需要 chroot 侧补的能力

| 能力 | 现状 | 需求 |
|---|---|---|
| `snapshot delete <name> --apply` | 无 | 系统页删除快照；R2/R3 确认 |
| `snapshot list --json` | 有 | 补 `state_bytes`、`last_good_bytes` |
| `status --json` | 有 | 补 `uptime_s`（省得客户端算） |
| 结构化日志 | 无（拼文本后客户端过滤） | `dsh-ctl log --json --kind X --lines N` |
| 任务步骤 | 无（自由文本） | 约定行前缀 `#step: <name>`，控制台据此渲染步骤 |
| `diag --json` | `diag` 只有文本 | 输出可复制的诊断包（事实+最近日志+doctor 摘要） |
| `app version --json` | 无 | 在 guest 内取 DSH 版本、node/pnpm 版本、安装来源 |
| `app deps --json` | 无 | 列出 `dsh-*` 依赖与当前/可用版本 |
| `app upgrade/rollback --apply` | 无 | 升降级 DSH 或单个依赖，先自动导出 lockfile 备份 |
| `app plugins --json` | 无 | 列出已装插件与启用状态（来自 profile/patch） |
| `ttyd status --json` | 仅文本 | 控制台开终端前需要端口/进程状态（软件页现在只能显示"状态待上报"） |
| `status --json` 的抽稀 | 字段偏多 | 控制台只需要 `state/pid/loop/image/url/rootfs_mounted/loop_query/residual_resources/watchdog_running/autostart/health_age/image_bytes`，其余字段可留给 `--verbose` |
| `log --follow` / `log --json` | 无 | C1 任务条要边跑边看到日志 |
| `#step: <name>` 步骤行 | **已实现**（`DSH_STEPS=1` 时输出，默认关闭）：`dsh_step` 在 `module/lib/common.sh`，`start` 8 步、`stop` 1 步、`snapshot restore` 4 步 | 任务时间线；后续给 `image install`、`purge` 补 |

注意：`app *` 系列必须在 guest 内执行（node/pnpm 在 rootfs 里），实现上是 `dsh-ctl` 进入 chroot 跑一个小的 guest 侧脚本，控制台只消费 JSON，不自己跑 pnpm。

## 13. 已定（2026-10-31）
